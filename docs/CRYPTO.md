## 1. 为什么密码无法找回，只能重置

这是理解整个设计的前提，值得单独讲清楚。

### 1.1 一个逻辑上的不可能

加密产品的核心承诺是：

> **连开发者本人也打不开你的笔记。**

而"能帮你找回密码"要求：

> **有一个除你之外的人（或机制）知道你的密码。**

这两句话不能同时为真。若密码能以任何形式被还原——明文、可逆编码、或用固定密钥加密后存放——那么拿到你文件的人也能做同样的事。**那不是加密，那是记录。**

所以任何声称"能找回密码"的本地加密产品，只可能是三种情况之一：

| 声称 | 真相 |
|---|---|
| "我们能找回你的密码" | 密码被存下来了（可还原），安全性归零 |
| "用密保问题找回" | 密保答案是**更弱的第二密码**，且提示通常公开，等于泄露信息 |
| "服务商可帮你重置" | 有人替你保管密钥，端到端加密失效 |

### 1.2 正确的目标：保住数据，不是找回密码

你真正在乎的不是"那串字符"，而是"我的笔记还在不在"。这两件事可以分开：

```
你忘记的          →  只是"包装钥匙的盒子"
你真正需要的      →  是"钥匙本身"（数据密钥，还在）
```

于是正确的方案是**凭据重置（credential reset）**：

| 操作 | 结果 | 代价 |
|---|---|---|
| **重置密码** | 用恢复密钥取出同一把数据密钥，再用新密码重新包装 | 写几百字节，毫秒级，笔记零改动 |
| ~~找回密码~~ | 不可能，见 1.1 | — |

**术语区分（重要）：**

- **密码找回（password recovery）**：还原出原密码。本插件**不做**，因为它不成立。
- **凭据重置（credential reset）**：用另一种凭据重新获得访问权，并设置新密码。本插件**做这个**。
- **数据恢复（data recovery）**：文件损坏后修复内容。本插件只做有限支持（`backups/` 保留最近 5 份密文）。

UI 里我们统一说"重置"，不说"找回"。这不是文字游戏——说错了会让用户误以为丢了恢复密钥也没关系。

## 2. 信封加密：整个设计的核心

### 2.1 问题

如果直接用"密码派生的密钥"加密每篇笔记，换密码就必须**重新加密所有笔记**。对 800 篇笔记的库意味着：

- 慢：每篇跑一次 PBKDF2，累计 60–90 秒
- 危险：中途崩溃/断电/同步冲突 → 一部分新密文、一部分旧密文，可能永久打不开
- 浪费：内容一个字没变，凭什么重写？

### 2.2 解法

引入一把**随机生成的数据密钥（DEK）**，让它成为唯一真正加密内容的钥匙。密码只负责"打开装 DEK 的盒子"。

```
                     ┌─────────────────────────────┐
   主密码 ──PBKDF2──▶ │ KEK_pw  ──解开──┐           │
                     └─────────────────┤           │
                     ┌─────────────────┤  ┌────────┴────────┐
   恢复密钥 ─PBKDF2─▶ │ KEK_rec ──解开──┼─▶│   DEK（32 字节） │
                     └─────────────────┘  │   真正的钥匙     │
                     ┌─────────────────┐  └────────┬────────┘
   动态密码种子 ─PBKDF2▶│ KEK_totp ─解开─┘           │
                     └─────────────────┘            │ HKDF + 每篇盐
                                          ┌─────────┴─────────┐
                                          ▼                   ▼
                                     笔记文件密钥        内联块密钥
                                          │                   │
                                     AES-256-GCM         AES-256-GCM
```

**由此得到三个直接好处：**

1. **改密码 = 只重新包装 DEK**。写一个几百字节的文件，原子操作，所有笔记立刻可用新密码打开。
2. **忘记密码 = 用恢复密钥取出同一个 DEK**，重设密码。数据一行不动。
3. **只有 DEK 泄露才需要全库重加密**。这是显式的高级操作，不是日常路径。

### 2.3 为什么叫"信封"

想象把钥匙装进信封，信封上写着"用你的指纹才能拆"。换指纹只是换信封，钥匙没动。这就是 envelope encryption。

## 3. 术语表

按字母与重要性排列。**粗体**是核心概念。

| 术语 | 全称 | 在这个插件里指什么 |
|---|---|---|
| **AAD** | Additional Authenticated Data | 附加认证数据。参与完整性校验但**不加密**的公开数据。我们用它把密文"绑定"到特定用途，防止密文被搬到别处复用 |
| **AEAD** | Authenticated Encryption with Associated Data | 同时提供机密性与完整性认证的加密模式。AES-GCM 属于此类 |
| **AES** | Advanced Encryption Standard | 对称加密标准。我们用 256 位密钥版本 |
| **Base32** | — | 用 A–Z 和 2–7 编码二进制。恢复密钥用它，因为**不含容易看错的 0/1/8/9**，适合手抄 |
| **Base64** | — | 用 64 个字符编码二进制。密文在 Markdown 里用它，因为紧凑 |
| **DEK** | Data Encryption Key | **数据密钥**。32 字节随机数，唯一真正加密内容的钥匙。永不裸存 |
| **GCM** | Galois/Counter Mode | AES 的一种工作模式，提供加密 + 认证。密文末尾附 16 字节 tag |
| **HKDF** | HMAC-based Key Derivation Function | 从高熵密钥派生多个子密钥。**快**，用于从 DEK 派生每篇密钥 |
| **IV** | Initialization Vector | 初始化向量。12 字节随机数，确保**相同明文每次加密结果不同**。与密文一起存，不需要保密 |
| **KEK** | Key Encryption Key | **密钥加密密钥**。由人类凭据派生的密钥，只用来加密/解密 DEK |
| **key copy** | 密钥副本 | 存放在每篇 `.sealed.md` 里的"被包裹的 DEK"，不是独立文件 |
| **KDF** | Key Derivation Function | 密钥派生函数。把弱的人类密码变成强密钥 |
| **PBKDF2** | Password-Based Key Derivation Function 2 | 慢速 KDF。用 600,000 次迭代，**故意让暴力破解变慢** |
| **Salt** | 盐 | 随机数，参与密钥派生。确保相同密码在不同处派生出不同密钥，让彩虹表失效。**公开存储** |
| **Slot** | — | 密钥槽。keyring 里的一组记录，对应一种解锁方式（password / recovery / totp） |
| **SubtleCrypto** | — | 浏览器原生加密 API（`crypto.subtle`）。我们用它的实现，不自己写密码学 |
| **TOTP** | Time-based One-Time Password | 基于时间的一次性密码（RFC 6238）。就是"动态密码"、"两步验证"里的 6 位数字 |
| **Tag** | Authentication Tag | 认证标签。GCM 产生的 16 字节校验值。密文被改一个 bit，tag 就对不上，解密直接失败 |
| **Wrapping** | Key Wrapping | 密钥包裹。用 KEK 加密 DEK 的过程 |
| **迭代次数** | Iterations | PBKDF2 重复次数。越高越慢越安全。我们存 600,000，且**拒绝低于 100,000 的文件** |
| **Epoch / Generation** | — | 版本号。每次改密钥就 +1，用于检测回滚 |

### 3.1 两个容易混淆的概念

**加密 ≠ 编码**

- Base64 是**编码**，不是加密。任何人 base64-decode 就能看到内容。我们只把 base64 用于"把二进制塞进文本文件"，安全性靠底下的 AES-GCM。
- 看到 `sn1.eyJ...` 觉得"看不懂所以安全"是错的。看不懂是因为它是密文，不是因为是 base64。

**哈希 ≠ 加密**

- 哈希单向不可逆，加密可逆（有钥匙）。
- 我们不存密码哈希，因为存了就给了离线爆破的目标。我们存的是**用密码派生密钥加密后的 DEK**——猜错密码就解不出 DEK，等价于验证，但不留可爆破的哈希。

### 4.0 唯一存储路径：笔记自己

```
    .sealed.md 笔记的 keys 字段
    （每篇都有，随普通同步走）
              │
              ▼
     解出同一把 DEK ──▶ 打开全部笔记
```

没有第二份密钥文件，没有隐藏目录。**笔记在，密钥就在。**

早期设计有一个独立的 `keyring.json`，但它放在 `.obsidian/` 里——Remotely Save 默认不同步隐藏目录，重装插件也会清空它。这是比磁盘损坏常见得多的失效方式，所以删掉了。

### 4.1 为什么 AAD 要绑定 slot 和 generation

AAD 参与认证但不加密。如果攻击者把 `password` 槽的密文搬到 `recovery` 槽，**没有 AAD 的话解密仍然成功**（因为用的是同一把 DEK、同样的算法）。加上 AAD 后：

```
slot=password 的 AAD = "…|password|g1"
挪到 recovery 槽后，程序会用 "…|recovery|g1" 去验证 → tag 对不上 → 拒绝
```

`gen` 也能防篡改某个槽的数字。整格原样还原仍可能，但删除独立密钥文件后，密钥副本与内容同在一个文件里一起回滚，是自洽的（见第 7 节）。

### 4.2 为什么笔记的 AAD 不含 generation

这是刻意的。改密码会 `gen++`，如果笔记 AAD 绑定 gen，那么**每次改密码都要重写所有笔记**——正好破坏信封加密的核心优势。

笔记的 AAD 只绑定 `vaultId`。效果：

- 改密码 → 笔记内容（`data`）一个字节都不用动 ✅
- 把笔记从别人的库拷过来 → AAD 不匹配，解不开 ✅
- 把笔记从旧备份还原 → 能解开（内容没变，安全）✅

## 5. 凭据生成与解锁架构

> TOTP 的扫码流程、验证码算法、时间来源的完整推导见 [TOTP-PRINCIPLE.md](TOTP-PRINCIPLE.md)。

### 5.1 三条凭据从哪来

```
┌──────────────────┐ ┌──────────────────┐ ┌──────────────────┐
│ 主密码           │ │ 恢复密钥         │ │ TOTP 种子        │
│ 你设置，≥10 字符  │ │ randomBytes(20)  │ │ randomBytes(20)  │
│                  │ │ → Base32 32字符  │ │ → Base32 32字符  │
│ 只在你脑子里     │ │ 抄在纸上，离线   │ │ 二维码给手机扫走 │
└────────┬─────────┘ └────────┬─────────┘ └────────┬─────────┘
         │                    │                    │
         │ 你想出来的          │ 只随机生成一次     │ 只随机生成一次
         │ 插件不生成不保存    │                    │
         ▼                    ▼                    ▼
    credentialFor()   credentialFor()     credentialFor()
    "sn-pwd|…"        "sn-rec|…"          "sn-totp|…"
         │                    │                    │
         └────────────────────┼────────────────────┘
                              ▼
              PBKDF2-HMAC-SHA512（600,000 次 + 独立盐）
                              ▼
                            KEK
                              ▼
                    AES-GCM(KEK, DEK)
                              ▼
              笔记的 keys.slots.{slot}.wrap
```

**关键点**：只有恢复密钥和 TOTP 种子是随机生成的（各 160 位）；主密码由用户想出来，插件既不生成也不保存。三者都经过域前缀包装再派生，所以同一个字符串不会被当成不同凭据误用。

### 5.2 四种解锁方式，一把 DEK

```
┌────────────┐ ┌────────────┐ ┌────────────┐ ┌────────────┐
│ 纯主密码   │ │ 纯动态密码 │ │ 密码+动态  │ │ 恢复密钥   │
│            │ │            │ │            │ │            │
│ 输入：     │ │ 输入：     │ │ 输入：     │ │ 输入：     │
│ 主密码     │ │ 6 位码     │ │ 密码+6位码 │ │ 52 字符    │
│            │ │ 种子从本机 │ │ 两个拼成   │ │ 任何模式   │
│            │ │ 恢复后验码 │ │ 凭据，缺一 │ │ 都可用     │
│            │ │ 再用种子解 │ │ 不可       │ │ 用于重设   │
└─────┬──────┘ └─────┬──────┘ └─────┬──────┘ └─────┬──────┘
      │              │              │              │
      └──────────────┴──────┬───────┴──────────────┘
                           ▼
              解开同一个 DEK（32 字节）
              四条路，一把钥匙，内容无需重加密
                           ▼
              HKDF-SHA256（域隔离：note/v1 · inline/v1）
                           ▼
                    AES-256-GCM 解开笔记
```

**纯动态模式的种子来源优先级**（这是"重启免扫码"的关键）：

```
① 本次粘贴的 otpauth 链接    ← 新设备 / 重新绑定
② sessionTotpSeed（内存）    ← 本次会话内复用
③ seedRef（设备密钥加密）    ← 同一台设备重启后静默恢复
```

- **同一台设备重启** → 走 ③，只输 6 位码，**不用重新扫码**
- **换新设备** → ③ 解不开，用主密码/恢复密钥先进去，粘一次链接重新绑定

### 5.3 三种模式可独立使用

| 模式 | 解锁所需 | 安全性来源 |
|---|---|---|
| `password` | 主密码 | 密码强度 × 60 万次迭代 |
| `totp` | 6 位码（种子从本机恢复） | 160 位种子在手机验证器 |
| `password+totp` | 主密码 + 6 位码 | 两者叠加，缺一不可 |
| 恢复密钥 | 52 字符 | 独立 slot，任何模式下都能重设 |

模式之间可以随时切换。切换只重包对应 slot，**DEK 不变，笔记一个字节不动**。

**首次初始化就能任选模式**，不需要先设主密码。`createKeyringWithoutPassword()` 可以先只写恢复 slot，再按选中的模式加 TOTP 和/或密码 slot。恢复密钥在任何模式下都生成，避免"选了纯动态、又丢了种子"时无路可走。

### 5.4 统一接口

```ts
interface UnlockProvider {
  id: "password" | "totp" | "password+totp" | "recovery";
  fields: ProviderField[];              // UI 由字段描述驱动
  unlock(kr, attempt): Promise<Uint8Array>;  // 返回 DEK
}
```

四条路，一个终点。这是"面向接口"的落点：将来加通行密钥（Passkey）、系统钥匙串，只需实现这个接口并注册。

### 5.5 动态密码为什么这样设计

TOTP 有两个必须同时成立的条件：

1. **验证码正确** → 证明你持有身份验证器（6 位码只做门禁，不参与加密）
2. **种子正确** → 160 位种子才是密钥材料，用它派生 KEK 解 DEK

**为什么不用 6 位码当密钥**：20 位熵、每 30 秒变——枚举 100 万次就能破，且 30 秒后自己都解不开自己的笔记。

**为什么种子不全存在本机**：如果种子明文存在笔记里，拿到云端文件的人不需要你手机就能算码。所以明文种子只在手机验证器 + 解锁时的内存；本机那份是设备密钥加密的 `seedRef`，换设备解不开。

**诚实的边界**：动态密码是应用层门禁，不是密码学强制。绕过它不需要破译任何密文，改几行插件代码就行。真正的密码学根是恢复密钥。

## 6. 数据格式详解

### 6.1 密钥副本（在笔记的 `keys` 字段里）

不再有独立的 keyring 文件。包裹后的密钥存在每篇 `.sealed.md` 的 `keys` 字段里：

```json
"keys": {
  "vaultId": "b1f2c3d4-…",
  "epoch": 3,
  "kdf": { "hash": "SHA-512", "iterations": 600000 },
  "slots": {
    "password": {
      "gen": 2,
      "salt": "<16B Base64>",
      "wrap": { "iv": "<12B Base64>", "data": "<密文‖tag>" }
    },
    "recovery": { "…": "…" }
  }
}
```

**里面没有的东西（重要）：**

- ❌ 密码明文
- ❌ 恢复密钥明文
- ❌ DEK 明文
- ❌ 任何笔记内容

**迭代次数下限强制校验**：`iterations < 100000` 直接判定为非法。否则攻击者把 600,000 改成 1,000，爆破就能快 600 倍。

**TOTP 相关也在这里，但都是密文**：`slot.totp` 是用种子包裹的 DEK；`totp.seedRef` 是用设备密钥加密的种子。两者随笔记同步，但换设备后都解不开——所以换设备必须重新绑定。明文种子从不出现。

### 6.2 笔记文件 `.sealed.md`（单文件正文信封）

一个 `.sealed.md` 文件就是整篇隐私笔记，没有独立密文目录、没有注释锚点。锁定态正文是 HTML 注释包裹的 JSON 信封（渲染视图下不可见）：

```
<!-- sealed-note/note/1
{
  "format": "sealed-note/note/1",
  "kid": "b1f2c3d4-…",
  "salt": "<16B Base64>",
  "iv": "<12B Base64>",
  "data": "<密文‖tag>",
  "keys": { ... }
}
-->
```

解锁后同一文件的正文被替换为**纯明文**（不带任何注释）；锁定时再换回信封。

- `kid` 用于识别属于哪个密钥库（明文，但也只是个 UUID）
- **文件名是明文**——`2026-财务密码.sealed` 这个名字本身就是信息，敏感场景请用中性命名

### 6.3 内联载荷

```
sn1.<Base64( salt8 ‖ iv12 ‖ ciphertext ‖ tag16 )>
```

出现在两种位置：

- 围栏块：```` ```encrypted_txt ```` 里
- 行内：`` `sn1.xxx` ``

**载荷里没有 JSON 开销**，因为内联块通常很短，省字节。代价是不能像笔记那样自描述，所以版本号放在前缀 `sn1` 里。

### 6.4 三种加密对象的写入流程

```
① 整篇隐私笔记（新建 / Ctrl+S / 停止输入 1.5 秒）
   明文 + keys副本
        │
        ├─ randomBytes(16) → salt
        ├─ HKDF-SHA256(DEK, salt, info="sealed-note/note/v1") → 子密钥
        ├─ randomBytes(12) → IV
        └─ AES-GCM(子密钥, 明文, AAD=vaultId) → data‖tag
                    │
                    ▼
        { format, kid, salt, iv, data, keys }  → xxx.sealed.md
        （atomicWrite：写 .tmp → rename，覆盖前自动备份最近 5 份）

② 内嵌加密块 / 行内密文（在普通 .md 里）
   选中文字
        │
        ├─ randomBytes(8) → 短盐（省字节）
        ├─ HKDF-SHA256(DEK, salt, info="sealed-note/inline/v1") → 子密钥
        ├─ randomBytes(12) → IV
        └─ AES-GCM → ciphertext‖tag
                    │
                    ▼
        sn1.<Base64(salt8 ‖ iv12 ‖ ciphertext ‖ tag16)>
        块：```encrypted_txt ... ```
        行内：`sn1.xxx`（Ctrl+点击 → 直接进剪贴板，不上屏）

③ 三者的共同点
   - 同一把 DEK，不同 HKDF info 域隔离 → 整篇的密钥解不开行内
   - 每次加密都换新的 salt/IV → 相同明文两次加密结果不同
   - 只有 ① 带 keys 字段（自描述）；②③ 靠 vault 的密钥库解开
```

**读流程是上面逆过来**：解出 DEK → 用 envelope 里的 salt 派生子密钥 → AES-GCM 验证 tag → 出明文。tag 不对就拒绝，不返回任何部分明文。

## 7. 为什么彻底删掉 keyring 文件

### 7.1 原本的设计有个真实缺陷

最初把包裹后的 DEK 放在一个 `keyring.json` 里，位于插件目录 `.obsidian/plugins/sealed-note/`。

问题是这个位置**恰好是最容易被跳过同步的地方**：

- Remotely Save 默认不同步以 `.` 或 `_` 开头的文件/目录，`.obsidian` 是隐藏目录
- 重装插件会清空插件目录
- 用户为了避免配置冲突，经常主动排除 `.obsidian`

结果：笔记同步得好好的，密钥文件没了，全部笔记变成乱码。**这个概率远高于磁盘损坏**，而且是一次配置项就能造成的灾难。

### 7.2 解法：密钥跟着笔记走

彻底删除 keyring 文件。每篇 `.sealed.md` 笔记内嵌 `keys` 字段：

```json
{
  "format": "sealed-note/note/1",
  "kid": "…",
  "salt": "…",   "iv": "…",   "data": "…",
  "keys": {
    "vaultId": "…",
    "epoch": 3,
    "kdf": { "hash": "SHA-512", "iterations": 600000 },
    "slots": {
      "password": { "gen": 2, "salt": "…", "wrap": { "iv": "…", "data": "…" } },
      "recovery": { "gen": 1, "salt": "…", "wrap": { "iv": "…", "data": "…" } }
    }
  }
}
```

**关键性质**：所有笔记都由**同一把 DEK** 的 HKDF 子密钥加密。所以

> **任意一篇带密钥副本的笔记，足以恢复整个保管库**——不是只恢复那一篇。

这是信封加密意外带来的红利：DEK 全局唯一，所以副本天然可以互相替代。

### 7.3 代价与应对

| 代价 | 应对 |
|---|---|
| 解锁前要扫一遍笔记找最高 epoch | 800 篇约几百毫秒；可缓存到内存 |
| 改密码要更新所有笔记的 `keys` | 只改这一个 JSON 字段，`data` 原样拷贝；PBKDF2 只跑一次 |
| 批量更新中途失败 | 幂等可续跑：已是当前代的直接跳过，内容永不受损 |
| 普通 Markdown 会不会被误改 | 只按 `.sealed.md` 识别，其他文件不打开 |

### 7.4 关于“回滚攻击”

删除 keyring 文件后，**独立文件的回滚概念不再存在**。密钥副本和笔记内容在同一个文件里，一起同步、一起回滚。

这带来一个新性质：如果同步工具把某篇笔记回滚到旧版本，那篇笔记的**内容和密钥副本一起回到旧状态**（自洽，仍可解开）。不存在“内容新、密钥旧”的错位状态。

早期我说“AAD 绑定 gen 可防回滚”，那是过度承诺。单格 `gen` 只能防篡改和跨 slot 移植；整格原样还原时 `gen` 会跟着回来。现在把密钥放进笔记后，这个限制不再紧要——因为每个文件是自洽单元。

### 7.5 关于“导出恢复包”

曾有想法：把 `keys` 字段单独导出成文件离线保管。

**不实现。** 理由：

- 恢复密钥本身就是那个“离线保管的秘密”——它直接派生 KEK 解开 DEK
- `keys` 字段**已经在每篇笔记里随同步走了**，再导出一份是冗余
- 它救不了任何恢复密钥救不了的场景：所有笔记丢了，导出的密钥也救不回不存在的内容
- 多一个需要保管的文件，与目标矛盾

**你唯一需要离线保管的，只有那串恢复密钥。**

## 8. 每个文件的职责（哪些能丢）

| 文件/凭据 | 位置 | 丢了会怎样 | 必需性 |
|---|---|---|---|
| **恢复密钥** | 你的纸上 / 密码管理器 | 忘了密码时彻底没救 | 🟡 忘了密码时必需 |
| **主密码** | 你脑子里 | 用恢复密钥重设 | 🟡 可补救 |
| **`.sealed.md` 笔记** | 保管库（正常同步） | 内容没了，但其他笔记仍有密钥 | 🔴 内容本身 |
| 动态密码种子 | 本设备 localStorage | 用密码解锁后重新绑定 | 🟢 可替代 |
| `backups/` | 插件目录 | 失去历史版本，不影响当前 | 🟢 冗余 |

**没有任何单独的密钥文件。** 插件目录只有 main.js / manifest.json / styles.css / tools/。

### 8.1 真正的全灭条件

只有两种：

1. 所有笔记 + 恢复密钥同时丢失
2. 所有笔记都是旧版本、不带 `keys` 字段，且同步密钥文件也丢了

第 2 种只发生在从早期版本迁移的库。迁移方法：打开每篇笔记保存一次，或运行一次「刷新所有加密笔记里的密钥副本」。

## 8b. 凭据泄露后能否重新生成

三种凭据都是"包裹 DEK 的盒子"，都能重新生成，且**都不重加密笔记内容**（DEK 不变）。

| 泄露了 | 操作 | 旧凭据 | 手机扫码 | 前提 |
|---|---|---|---|---|
| 主密码 | 纯密码模式：`changePassword(dek, newPw)` 重包 password slot。组合模式：只重包 password-totp 组合槽（严格双因子，没有单独的 password slot），且需本机种子 | 立即失效 | 不用 | 能解锁；组合模式还需本机有种子，否则去「恢复本机种子缓存」导入后再改 |
| 恢复密钥 | `replaceRecovery(dek, newRec)` 重包 recovery slot | 立即失效 | 不用 | **先确认新密钥已安全保存**，否则把自己锁外面 |
| TOTP 种子 | `configureMode(dek, mode, { seed: 新种子 })` 重包 TOTP slot | 立即失效 | **要，新种子必须重新扫码** | 能解锁进设置 |

### 关键限制：换盒子不追回过去

这是最容易被误解的一点。三种凭据泄露后重新生成，只保护**未来**：

- ✅ 旧密码/旧恢复密钥/旧种子**今后**打不开
- ❌ 如果攻击者**已经**拿到了「笔记文件 + 泄露的那把凭据」，他早就解出 DEK、解开全部笔记了。你换盒子，他手里的明文不会消失

换句话说：换凭据 = 换门锁，**不能让已经进过屋的人把看过的东西忘掉**。

真正的止损手段（如果怀疑已经泄露）：

1. 换凭据（阻止未来访问）
2. 把内容视为已泄露——改掉里面记录的密码/令牌，**这是唯一能让旧信息失效的动作**
3. 若连 DEK 都可能泄露，需要"轮换 DEK + 全库重加密"——当前版本**没有**这个一键功能，只能建新库再迁移

### 一句话总结

| 问题 | 换凭据能解决吗 |
|---|---|
| 旧凭据以后还能不能用 | ✅ 能，立即作废 |
| 已经看过的笔记内容 | ❌ 不能，内容靠 DEK，得改内容本身 |
| DEK 本身泄露 | ❌ 需要全库重加密（当前无此功能） |

## 8c. 什么情况下会真正重加密内容

先区分两个词，它们在代码里完全不同：

- **重写文件**：文件被写了一遍，但 `data`/`salt`/`iv` 字节原样拷贝
- **重加密内容**：用 DEK 重新跑 AES-GCM，`data` 全变

代码事实：`newDek()` 只在 `createKeyring()`（建库）里调用，**没有任何"改 DEK"的代码**。所以：

### 会真正重加密的场景（内容变了）

| 场景 | 路径 | 说明 |
|---|---|---|
| **你编辑笔记内容后保存** | `writePlaintext()` → `sealNote(DEK, 新明文)` | 唯一日常重加密。DEK 没变，但明文变了，所以密文变 |
| **建新库 + 迁移**（唯一的"全库重加密"） | 新 DEK → 逐篇解密旧笔记 → 用新 DEK 加密到新库 | 当前版本**没有一键功能**，只能手动迁移。用于怀疑 DEK 泄露 |

### 只重写文件、不重加密的场景（内容一个字节不动）

| 操作 | 实际改动 |
|---|---|
| 改主密码 | 只换 `keys.slots.password` 的包裹 |
| 重置恢复密钥 | 只换 `keys.slots.recovery` |
| 重新绑定/生成 TOTP 种子 | 只换 `keys.slots.totp` |
| 切换解锁模式 | 只换对应 slot 的包裹 |
| 刷新密钥副本 | 只同步 `keys` 字段（幂等，已是最新就跳过） |
| 恢复本机种子缓存 | 只换 `keys.totp.seedRef` |

实现都是 `{ ...envelope, keys: 新副本 }`——`data` 原样拷贝。即使中途断电，最坏是密钥副本过期，**笔记内容永远完好**。

### 改密码时批量刷新副本的流程

```
用户确认新密码
      │
      ├─ PBKDF2(新密码, 新盐, 600k) → 新 KEK（只跑这一次）
      │
      ├─ AES-GCM(新KEK, DEK) → 新的 slot 包裹
      │    （纯密码模式 → password slot；组合模式 → password-totp 组合槽）
      │
      ▼
扫描 vault 里所有 .sealed.md
      │
      ├─ 对每篇：解析 envelope
      ├─ 判断 keys.epoch：已是最新 → 跳过（幂等，不动文件）
      │                 旧 → 只替换 keys 字段
      │
      ├─ atomicWrite：写 .tmp → rename（覆盖前备份）
      │
      ▼
结果：N 篇笔记的 data/salt/iv 字节完全没变，只有 keys 变了
      普通 .md 一个都不碰（按 .sealed.md 路径识别）
```

**为什么 PBKDF2 只跑一次**：KEK 是全局的（同一个密码包同一个 DEK），所以派生一次就够，之后 N 次只是把同一个新盒子抄进 N 篇笔记——这是 PBKDF2 600k 次迭代能承受的关键。如果每篇都跑一次 PBKDF2，改一次密码要算 N × 600k 次，完全不可用。

**中断续跑**：中途关掉 Obsidian 不会损坏内容。重跑时已是最新 epoch 的笔记自动跳过，只补完剩余的。

### 一句话

除了"你编辑了内容并保存"和"手动建新库迁移"，**没有任何操作会重加密你的笔记**。改密码、换种子、切换模式，全都只换"装 DEK 的盒子"。

## 9. 威胁模型

### 9.1 能防住

| 威胁 | 为什么 |
|---|---|
| 云同步泄漏（坚果云/iCloud/Git） | 同步的只有密文 |
| 电脑被翻，但 Obsidian 已锁 | DEK 只在内存，切走即清零 |
| 笔记被搜索工具/AI 批量索引 | `.sealed` 不在 Markdown 索引里 |
| 拿到 vault + 知道你密码，但没有你手机 | 动态密码是第二道门 |
| 用 600k 迭代拖慢离线爆破 | 每次猜测约 0.3–0.5 秒 |

### 9.2 防不住（诚实清单）

| 威胁 | 说明 |
|---|---|
| **解锁状态下的内存读取** | 明文在内存和渲染层。恶意插件、调试器、内存转储都能拿到 |
| **截屏 / 录屏 / 剪贴板** | 解密到剪贴板 = 所有程序都能读，且不自动清空（那是补救不是防护，也会误伤后续复制）。用完记得自己清 |
| **文件名、大小、数量、修改时间** | 元数据是明文 |
| **键盘记录器** | 密码在输入时就被截获 |
| **被入侵的操作系统** | root 权限面前无解 |
| **弱密码 + 拿到 keyring** | 离线爆破。所以有强度提示，但**不强制**——强制会让用户写墙上 |
| **恢复密钥拍照存相册** | 云相册自动同步 = 把钥匙贴门上 |
| **硬件层面的侧信道** | 超出范围 |

### 9.3 一句话总结

> 这个插件保护**静态数据**（磁盘上的、被同步的、被备份的）。
> 它不保护**使用中的数据**（屏幕上的、内存里的、剪贴板里的）。

理解这条线，就知道什么时候该锁屏、什么时候该清剪贴板。
