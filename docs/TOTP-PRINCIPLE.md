## 1. 先纠正一个常见误解

**不是"生成 20 万个种子，扫码时从中选一个"。**

真实情况只有**一个种子**，一次性随机生成，之后固定不变。

```
生成时：  crypto.getRandomValues(20 字节)   ← 只做一次
          160 位随机数
          ↓ Base32 编码
          JBSWY3DPEHPK3PXPJBSWY3DPEHPK3PXP   ← 32 个字符
          ↓ 拼成 URI
          otpauth://totp/...?secret=JBSWY3D...
          ↓ 编码成图
          二维码
```

"20 万"这个数字可能来自对 6 位码的误解：6 位十进制码有 `10^6 = 1,000,000` 种可能（不是 20 万）。但那是**每次显示的临时验证码**，不是种子。

| 东西 | 数量 | 变化频率 | 作用 |
|---|---|---|---|
| 种子 secret | 160 位随机（Base32 后 32 字符） | **永不变化** | 真正的密钥材料 |
| 6 位验证码 | 100 万种可能 | 每 30 秒变 | 证明你持有种子 |
| 计数器 T | 随时间增长 | 每 30 秒 +1 | 计算的输入之一 |

## 2. 二维码里到底装了什么

二维码**不是什么特殊协议**，它只是把一串文本编码成黑白方块。这串文本是一个标准格式的 URI：

```
otpauth://totp/Sealed%20Note:MyVault?secret=JBSWY3DPEHPK3PXPJBSWY3DPEHPK3PXP&issuer=Sealed%20Note&algorithm=SHA1&digits=6&period=30
```

拆开看：

| 部分 | 含义 |
|---|---|
| `otpauth://totp/` | 固定前缀，告诉 App 这是 TOTP 类型 |
| `Sealed%20Note:MyVault` | 显示名称（保管库名），URL 编码 |
| `secret=...` | ** Base32 编码的种子**——真正重要的部分 |
| `issuer=Sealed%20Note` | 发行方，App 里分组显示用 |
| `algorithm=SHA1` | 哈希算法，RFC 6238 规定 |
| `digits=6` | 显示几位 |
| `period=30` | 多少秒换一次 |

**这个格式是 Google Authenticator 在 2010 年左右定的事实标准**，所有主流 App（Authy、1Password、Microsoft Authenticator、Bitwarden）都支持。所以插件生成的二维码能被它们扫。

二维码本身只是这串文字的另一种表现形式。你用文本编辑器打开二维码图片看不到文字，但那只是编码——**没有任何加密**。

> ⚠️ 所以二维码和 otpauth 链接等价于种子本身。谁能看到它，谁就有了你的第二因素。
> 这就是为什么插件本地生成二维码、绝不调用在线二维码服务。

## 3. 扫码那一步发生了什么

```
手机摄像头
   ↓ 识别黑白方块，还原出 URI 字符串
Authy 解析 URI
   ↓ 读出 secret=JBSWY3D...
Base32 解码 → 20 字节二进制种子
   ↓
存进 App 的本地加密存储
   ↓
列表里出现一条 "Sealed Note: MyVault"
```

**关键点：扫码是纯本地操作。**

- 手机不需要联网来"验证"这个种子
- 没有任何服务器参与
- 数据从二维码直接进 App 存储

Authy 这类 App 的云备份是**可选功能**，和扫码本身无关。如果开了备份，种子会被 Authy 用自己的密钥加密后上传——那是 Authy 的安全模型，不是 TOTP 协议的一部分。

**扫码后手机工作了吗？** 是的，但只是存了个种子。只有在你打开 App 看验证码时，它才用种子 + 当前时间算一次 6 位码。

## 4. 6 位验证码是怎么算出来的

这是 RFC 6238 定义的 TOTP 算法。**整个计算只需要种子和时间，不需要网络。**

### 第 1 步：算时间计数器

```
T = floor(Unix 时间戳 / 30)
```

例如 `2026-11-22 12:00:10` 的时间戳是 `1763793610`：

```
T = floor(1763793610 / 30) = 58793120
```

每 30 秒 T 加 1。这就是验证码"每 30 秒变一次"的来源。

### 第 2 步：HMAC-SHA1

把 T 写成 8 字节大端整数，作为消息；种子作为密钥：

```
HMAC = HMAC-SHA1(key=种子20字节, message=T的8字节大端)
```

得到一个 20 字节的哈希值。

### 第 3 步：动态截取（dynamic truncation）

从 HMAC 里取出 4 字节，拼成一个 31 位整数：

```
offset = HMAC[19] & 0x0F        // 用最后一个字节的低 4 位当偏移
binary = (HMAC[offset] & 0x7F) << 24
       | (HMAC[offset+1]     ) << 16
       | (HMAC[offset+2]     ) << 8
       | (HMAC[offset+3]     )
```

`& 0x7F` 去掉最高位，确保是正数（避免不同语言整数符号差异）。

### 第 4 步：取模得到 6 位

```
code = binary % 1,000,000
显示 = code 左补零到 6 位
```

### 完整例子

插件的 `src/core/totp.ts` 就是这么实现的，可以用 RFC 6238 的官方测试向量验证：

```
种子 = ASCII "12345678901234567890" 的 Base32
时间 = 59 秒    → 287082
时间 = 1111111109 秒 → 081804
时间 = 1234567890 秒 → 005924
```

这 6 个向量都写进了测试，每次 `npm test` 都会跑。所以这不是我自己编的算法，是和 RFC 对齐的。

## 5. 时间从哪里来

你问"根据互联网时间选得到随机数吗"——**时间确实是关键输入，但不是用来"选随机数"，而是用来算计数器 T**。

### 时间来源

| 设备 | 时间来源 |
|---|---|
| 手机 | 本机时钟（通常由运营商网络或 NTP 校准） |
| 电脑 | 本机时钟（由操作系统 NTP 校准） |

**TOTP 协议本身不联网**。它只读本机时钟。所谓"互联网时间"只是"你的设备时间被网络校准过"的意思。

### 时间不准会怎样

如果手机快了 2 分钟：

```
手机算的 T = 电脑算的 T + 4
验证码完全不同 → 验证失败
```

这就是 TOTP 最常见的故障原因。解法是开启手机的"自动设置时间"。

### 为什么不用网络时间直接同步

因为那会引入依赖：没网就解不开。TOTP 的设计目标之一就是**离线可用**。代价就是要求双方时钟大致一致（在 ±30 秒内）。

## 6. 为什么 ±1 步容错

插件验证时允许前后各一个时间步（±30 秒）：

```
验证 code 时：
  试 T-1 的期望值
  试 T   的期望值
  试 T+1 的期望值
  任意一个匹配 → 通过
```

原因很实际：

- 你看到验证码的那一刻，可能刚好跨过 30 秒边界
- 你打字需要 2–5 秒
- 手机和电脑时钟可能差几秒

±1 步覆盖总共 90 秒的窗口，足够人操作。超过这个范围就拒绝——这限制了重放攻击的时间窗口。

**为什么不无限容错？** 因为验证码是 6 位（100 万种），如果允许 100 个时间步，攻击者猜中的概率就放大 100 倍。

## 7. 为什么它安全

安全性来自三个层面：

### 7.1 种子是高熵的

160 位随机 = `2^160` 种可能 ≈ `1.46 × 10^48`。

攻击者拿到二维码图片能读到种子——但二维码在你手里，不在攻击者手里。**攻击者拿到的是加密笔记和里面的密钥副本，那里面没有种子**。

### 7.2 种子不在 vault 里

这是这个插件的核心设计：种子只存在于你的手机验证器中。

| 攻击者拿到 | 能否解开笔记 |
|---|---|
| 云端同步的笔记 | ❌ 没有种子 |
| 笔记 + 你的主密码（双因子模式） | ❌ 还需要验证器 |
| 笔记 + 主密码 + 恢复密钥 | ✅ 能（这是恢复路径，设计如此） |
| 你的手机 | ✅ 能（那你已经全丢了） |

### 7.3 验证码一次性

验证码每 30 秒变，且验证时只允许 ±1 步。即使有人看到你输的验证码，30 秒后也失效了。

## 8. 为什么 6 位码不能直接当密钥

这是最关键的一点，也是这个插件的设计核心。

### 6 位码只有 20 位熵

`log2(1,000,000) ≈ 19.93` 位。

如果用它派生加密密钥（KEK）：

```
攻击者拿到笔记（含被包裹的 DEK）
  → 枚举 0 到 999999
  → 每个跑一次 PBKDF2
  → 试 AES-GCM 解密，tag 匹配就成功
```

100 万次 PBKDF2 对现代 GPU 不是难事。**这等于没有加密**。

### 6 位码每 30 秒变

假设你用 `287082` 加密笔记：

```
12:00:00 加密 → 用 287082
12:00:30 验证码变成 081804
12:01:00 你解密 → 需要 287082，但你只有当前的 081804
```

**笔记永远解不开了。**

### 正确做法

```
密钥材料 = 种子（160 位，固定不变）
验证码   = HMAC(种子, 时间) 的低 6 位，只用于验证
```

插件里的实现：

```ts
// 验证：证明你持有验证器
await verifyTotp(seed, code)

// 解锁：用种子派生 KEK，解开 DEK
credentialFor(SLOT_TOTP, { totpSeed: seed })
// → "sn-totp|JBSWY3D..."
// → PBKDF2(credential, salt, 600000)
// → AES-GCM 解开 DEK
```

6 位码**只出现在验证环节**，从不参与密钥派生。

## 9. 这个插件里的完整流程

### 9.1 首次设置

```
插件                                  手机
 │                                      │
 ├─ 生成 160 位随机种子                  │
 ├─ 拼成 otpauth:// URI                  │
 ├─ QRCode.toDataURL() 本地生成二维码 ──▶│ 扫码
 │  （不联网）                            ├─ 存种子到 App
 ├─ 显示二维码 + 密钥 + URI 备份          │
 │                                      │
 ◀──────────── 用户输入 6 位码 ──────────┤ HMAC(种子, 当前时间)
 │                                      │
 ├─ verifyTotp(seed, code)               │
 ├─ credentialFor(TOTP, seed)            │
 ├─ PBKDF2 → KEK                         │
 ├─ AES-GCM 包裹 DEK                     │
 └─ 写进加密笔记的 keys 字段              │
```

### 9.2 日常解锁（纯动态密码模式）

```
用户：打开一篇 .sealed.md
  ↓
插件：弹出解锁框，选"动态密码"
  ↓
用户：输入 6 位码 + 粘贴 otpauth 链接（首次）或复用会话种子
  ↓
插件：
  1. normalizeSeed() 从 URI 提取种子
  2. verifyTotp(seed, code) 验证 ±1 步
  3. credentialFor(TOTP, seed) 构造凭据
  4. PBKDF2(凭据, salt, 600k) → KEK
  5. AES-GCM 解开 DEK
  6. HKDF(DEK) → 笔记密钥
  7. AES-GCM 解开笔记内容
  ↓
显示明文（只在内存）
```

### 9.3 换电脑

```
新电脑装插件
  ↓
从手机验证器导出 otpauth:// 链接
  ↓
解锁框里"导入验证器链接"字段粘贴
  ↓
输入当前 6 位码
  ↓
解开（因为笔记里带着被包裹的 DEK，种子从手机来）
```

**不需要从旧电脑搬运任何东西。** 这是"种子跟人走，不跟设备走"的意义。

## 10. 种子会不会泄露？（服务器在哪里？）

一个常见疑问："扫码把种子加到手机，那 server 端的种子在哪？会不会泄露？"

### 没有 server

这个插件是纯本地 Obsidian 插件：

- 没有后端、没有账号、没有云端数据库
- 全部源码没有 `fetch`、`XMLHttpRequest` 或任何网络请求
- 打包产物里唯一的 `http://` 是 SVG 的 XML 命名空间（`www.w3.org/2000/svg`），用于渲染二维码

所以不存在"server 的种子"。**种子从没上过网。**

### 种子在代码里吗？

不在。代码里只有生成算法：

```ts
export function generateTotpSecret(): string {
  return toBase32(randomBytes(20));  // 每次调用现生成
}
```

没有任何硬编码的种子字符串。文档里出现的 `JBSWY3DPEHPK3PXP` 是 RFC 6238 的标准测试向量，不是生产种子。

### 种子的完整生命周期

| 时刻 | 位置 | 是否落盘 |
|---|---|---|
| 生成 | 插件内存 | 否 |
| 显示二维码/密钥 | 弹窗 DOM + 内存 | 否 |
| 你扫码 | 手机验证器 App | 是（在手机上） |
| 你点"启用" | 插件内存（验证 6 位码） | 否 |
| 解锁后 | `sessionTotpSeed` 会话内存 | 否，重启即失 |
| 配置/解锁时 | `seedRef`：设备密钥加密的种子副本，存在本机 localStorage | 是（仅本机，不同步） |
| 写进笔记的 | **只用种子派生出的 KEK 加密的 DEK** | 是，但不是种子 |

写进 `keys.slots.totp.wrap` 的是：

```
AES-GCM( PBKDF2("sn-totp|种子", salt, 600000), DEK )
```

里面有 salt、iv、密文——**没有种子、没有 KEK、没有明文 DEK**。攻击者拿到云端同步的笔记，面对的是被 160 位随机种子保护的密文。

### 真正的泄露面（都不是插件本身）

1. **二维码截图** —— 等于把种子发给看到图的人
2. **otpauth 链接存到云笔记明文** —— 同步到云端
3. **手机中木马** —— 验证器存储被读
4. **Authy 云备份账号失守** —— 那是 Authy 的安全模型，不是 TOTP 协议的一部分

### 必须承认的信任点

首次设置时，插件必须短暂持有种子（它要验证你输入的 6 位码对不对）。这段时间种子在内存里。

严格地说，你在这里要信任插件代码不会偷偷上传种子。我验证了它不会（无网络调用），但这属于"信任本地代码"的范畴。要完全消除这类信任，需要硬件密钥（YubiKey / WebAuthn），那超出 Obsidian 插件的能力范围。

## 11. 种子在插件的哪里？多设备一致吗？

这一节回答三个最容易被问到、也最容易说错的问题。

### Q1：不是说插件不保存种子吗？那验证时种子在插件的哪里？

先纠正措辞：**"不保存"指不把明文种子写进笔记或上传到任何地方**。运行时插件内存里必须有种子，否则算不出期望值。

种子在插件里有三个来源，按优先级：

```ts
// src/services/unlock-service.ts
private sessionTotpSeed: string | null = null;   // ① 本次会话内存
```

```
① 你在设置页「恢复本机种子缓存」粘贴的 otpauth 链接（新设备/重新绑定）
② sessionTotpSeed（本次会话内复用）
③ kr.totp.seedRef → 用设备密钥解密出的种子（同一台设备重启后）  ← 新增，免重粘
```

第 ③ 条是关键：`configureMode` 设置动态密码时，会把种子用**设备密钥**加密后存成 `seedRef`。设备密钥存在 Obsidian 的 localStorage 里——**不进 vault、不被同步工具上传**。所以同一台设备重启后，插件能静默解出种子，你只输 6 位码即可。

### Q2：换设备怎么办？

新设备的 localStorage 是空的，`seedRef` 解不开。这时：

1. 先用主密码或恢复密钥解锁（这两种方式不依赖种子）
2. 从手机验证器导出 otpauth 链接，粘贴一次
3. 插件把种子用**新设备的密钥**重新封存

之后这台设备重启也不用再粘。

**日常体验：只输 6 位码。只有换设备/重装才需要粘一次链接。**

### localStorage 被清空会怎样？

一个具体场景：Obsidian 的应用数据被清理、浏览器数据被清除、或系统清理工具删掉了 localStorage。

**会发生什么：**

| 东西 | 结果 |
|---|---|
| 手机 Authy 里的种子 | **不受影响**，6 位码照常显示 |
| 本机设备密钥（localStorage） | 丢失，下次会**重新生成一个全新的** |
| 旧的设备密钥封存的 `seedRef` | **解不开了**——新密钥 ≠ 旧密钥 |
| 结果 | 光输 6 位码不够，插件会要求你重新粘贴一次 otpauth 链接 |

**为什么不能像你猜的那样"重启自动重新生成、什么都不用做"？**

因为重新生成的是**设备密钥**，不是**种子**。设备密钥是新随机出来的，用它解不开旧密钥封存的种子。而种子绝不能明文存在笔记或云端（否则同步拿到文件的人不需要你手机就能算码）——所以它只能从手机验证器重新导出一次。

这跟"重新扫码到 Authy"是两回事：

- **设置时**：插件生成二维码 → 你用手机扫 → 种子进 Authy（一次性，永远不用重做）
- **本机缓存丢失时**：从 Authy **导出 otpauth 链接** → 粘贴给插件一次 → 插件用新设备密钥重新封存

手机那头完全不用动，种子没变，6 位码没变。粘一次之后，本机恢复"重启只输码"的日常状态。

> 已经把这条链路写成测试：清空 localStorage → 旧 `seedRef` 解不开 → 必须重粘 → 重粘后自动用新密钥封存 → 再重启只输码可用。

> 这正是你要求的：不能每次重启 Obsidian 都重新扫二维码 —— 那不是安全，是不可用。

### 设备密钥与"安全"的关系

有人会问："把种子存在本机，是不是又变成设备绑定了？"

不是。区别在于：

| 设计 | 换设备 | 安全性来源 |
|---|---|---|
| 设备密钥作为**解锁凭据** | 打不开（你否掉的方案） | 密钥绑死机器 |
| 设备密钥只**保护种子的本地副本** | 粘贴一次 otpauth 即可 | 种子在手机，设备副本只是缓存 |

`seedRef` 是加密后的缓存，且**不随笔记同步到真正有用的程度**——即使它出现在笔记的 `keys.totp` 里，别的设备也解不开（设备密钥不同）。真正的种子始终在你手机验证器里。

### Q3：每个设备的种子一样吗？不同手机看到的 6 位码一样吗？

**同一个 vault 只有一份种子。** 设置时生成一次，编码进二维码。所有设备扫的都是这一份。

因此：

- 你手机 Authy 里的种子 = 你解锁时粘贴的种子 = **同一个**
- 两台手机都扫同一个二维码 → 两台手机的种子**相同**
- 两台手机时间都准 → 显示的 6 位码**完全相同**

```
手机 A:  HMAC(同一个种子, 同一个 T) → 123456
手机 B:  HMAC(同一个种子, 同一个 T) → 123456
插件:    HMAC(粘贴的种子, 本机 T)   → 123456   ← 三者一致
```

反过来：

- 两台手机显示**不同**的码 → 它们导入的是**不同的种子**（扫了不同的二维码），或时间差超过 30 秒
- 这不是"每台手机一个码"，而是"同一个种子，同一时间，同一个码"

这也解释了为什么 TOTP 属于 "something you have"（你所拥有的东西）——你拥有的是那份种子，不是某台特定手机。谁拿到种子，谁就能算出和其他人一样的码。

### Q3a：既然算法是固定的，每次启动重新生成种子不行吗？

**不行。** 这混淆了"算法"和"算法的运行结果"。

算法固定不变：`toBase32(randomBytes(20))`、HMAC-SHA1、每 30 秒一步。但每次运行 `randomBytes(20)` 都产生不同的 160 位随机数，所以每次生成的种子都不同（实测四次：2VVURZ… / DPYKG4… / 3XPGDH… / MW3AGJ…）。

如果每次启动重新生成种子 S2，而手机里是设置时的 S1：

```
你输的码     = HMAC(S1, T)   ← 手机算的
插件期望     = HMAC(S2, T)   ← 插件算的
S1 ≠ S2  →  永远验证失败
```

**更致命的是第二层**：DEK 是被 S1 包裹的。插件拿 S2 连 DEK 都解不开，笔记直接永久锁死。

所以种子必须"固定"，且手机和插件两边一致。固定的位置只有三处：

| 存在哪 | 后果 |
|---|---|
| 手机验证器 | 必须有——这是第二因素的根 |
| 本机加密缓存（当前实现） | 重启免重粘 |
| 每次让你粘贴链接 | 每次都要翻密码管理器，不可接受 |

**没有第四条路**：不保存 + 每次自动生成 = 每次换一把新钥匙，而锁（被包裹的 DEK）是按旧钥匙配的。

### 本机种子丢了，在哪里操作恢复？

**只有一个入口：设置页。**

```
设置 → 解锁方式 → 「恢复本机种子缓存」→ 粘贴 otpauth:// 链接
```

解锁框里**故意不放**粘贴框。原因是一个死锁：

> 纯动态密码模式下，本机种子丢了 → 6 位码算不出来 → 解锁框打不开 → 进不去设置页 → 没法用设置页的恢复入口。

所以流程必须是：

```
本机种子丢了
   ↓
用【恢复密钥】解锁（它不依赖种子，任何模式都能进）
   ↓
设置 → 解锁方式 → 恢复本机种子缓存 → 粘贴链接
   ↓
恢复的是【同一个种子】，手机不用动，6 位码照常
   ↓
之后这台设备只输码即可
```

解锁框在检测到本机无种子时，会直接显示上述引导（不会让你在框里瞎粘）。

**这个方法的安全性**：写入前先验证导入的种子确实能解开当前 TOTP slot，验证通过才封存。粘错种子不会破坏 vault。

### 种子相关故障的完整决策图

```
输 6 位码解锁失败 / 提示"本机没有种子"
                    │
                    ▼
        手机 Authy 里还有这个 vault 的条目吗？
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
      【有】                   【没有】
  手机种子还在              手机种子也丢了
        │                       │
        ▼                       ▼
用恢复密钥解锁进设置      用恢复密钥解锁进设置
        │                       │
        ▼                       ▼
设置 → 恢复本机种子缓存    设置 → 解锁方式 → 更改
        │                       │
        ▼                       ▼
从 Authy 导出 otpauth     生成全新种子 → 新二维码
        │                       │
        ▼                       ▼
粘贴 → 验证能解开旧 slot   新手机扫码 → 验证新码
        │                       │
        ▼                       ▼
新设备密钥封存【原种子】   新设备密钥封存【新种子】
        │                       │
        ▼                       ▼
手机不动，6 位码照常      旧种子作废，用新码
```

**两条路的分水岭只有一个**：手机验证器里那份种子还在不在。在 → 恢复（不换种子、不扫码）；不在 → 重置（换种子、要扫码）。

**为什么第一条路也要恢复密钥**：纯动态模式下本机没种子就打不开解锁框，进不了设置页。恢复密钥不依赖种子，是唯一能让你"进门"的凭据。

### 不恢复行不行？只能靠恢复密钥"重置动态密码"吗？

可以，但要分清"恢复"和"重置"：

- **恢复**（设置页那个入口）：种子没变 → 手机不用动，6 位码照常
- **重置**（恢复密钥路线）：恢复密钥解出 DEK → 设置页点"更改" → **生成全新种子** → 手机重新扫码 → 旧种子作废

你说的"重新算出 localStorage 新种子"这个表述不准确：**种子不是从设备密钥算出来的**。设备密钥只负责加密种子。走恢复密钥路线时，种子是 `randomBytes(20)` 全新生成的，和设备密钥没有关系。

所以结论：**不操作恢复，确实只能走恢复密钥重置——但那样手机要重新扫码**。如果只是本机数据被清、手机种子还在，强烈建议用上面的入口恢复同一个种子，省事得多。

### 恢复密钥到底让你做什么？

准确说法不是"只是让你进去"这么简略，而是：

> 恢复密钥解出 DEK → 你拿着 DEK 可以重新包装**任何**凭据：改主密码、重新绑定种子、从 Authy 重新导入种子。所谓"重置"不是一个独立动作，而是"用 DEK 重新生成一个新盒子"的过程。

其中要分清两个动作：

| 动作 | 种子 | 手机 |
|---|---|---|
| 从 Authy **重新导入** otpauth 链接 | 同一个，不变 | 不用扫码 |
| **重新生成**种子 | 全新随机 | **必须重新扫码** |

### 组合模式（密码 + 动态）丢了某一项怎么办？

**关键事实**：组合模式是**一个盒子**——`sn-pwd-totp|密码|种子` 一起包裹 DEK，不是两个独立盒子。

| 丢了什么 | 恢复流程 | 手机扫码？ |
|---|---|---|
| 忘记主密码（种子还在） | 恢复密钥进 → 用 DEK 重包组合 slot（新密码 + 原种子） | 不用 |
| 丢设备密钥（手机种子在） | 恢复密钥进 → 从 Authy 重新导入原种子 → 重包 | 不用 |
| 丢 Authy 数据（种子没了） | 恢复密钥进 → 生成全新种子 → 重包 | **要** |
| 全丢 | 只有恢复密钥能救 | 视情况 |

**注意**：任何凭据变化都**不重新加密文档**。DEK 没变，笔记一个字节不动。变的只有解锁盒子。这不是"两个流程的合集"——是同一个动作（用 DEK 重包 slot），只是重包时填的新凭据不同。

### 到底有没有必须重新生成种子 + 扫码的场景？

**有，且只有一个**：手机验证器里的种子**物理丢失**。

- 换手机没迁移验证器
- Authy 账号数据找不回
- 删了 App 且没备份 otpauth 链接

**种子真的会丢**：它只是 32 个字符存在手机 App 里，不是什么云端永久绑定的东西。这正是设置时要你离线备份 otpauth 链接的原因——那是种子的唯一副本。

其他所有情况都不用换种子：

| 情况 | 换种子 | 扫码 |
|---|---|---|
| Obsidian 清了 localStorage | ❌ | ❌ 导入 otpauth 即可 |
| 换电脑装插件 | ❌ | ❌ 手机导出链接粘贴 |
| 忘记主密码 | ❌ | ❌ |
| 丢设备密钥 | ❌ | ❌ |
| **手机种子物理丢失** | ✅ | ✅ 必须重新扫码 |

### 术语纠正

"忘记动态密码"这个说法不准确。6 位码每 30 秒由种子现算，不会忘。真正会发生的是：

- **换手机 / 找不回 Authy 数据** → 手机那份种子丢了
- **清了 Obsidian 应用数据** → 本机那份加密缓存丢了

这两种的恢复方式不同，见下面两节。

### Q3b：手机验证器里的种子丢了，恢复密钥能救吗？

能，但要理解恢复密钥做了什么——它**不是用来生成种子的**。

`randomBytes(20)` 生成新种子不需要任何密钥，谁都能跑。恢复密钥的作用是**解出 DEK**：

```
恢复密钥 → 解开 recovery slot → 拿到 DEK
                                   ↓
randomBytes(20) → 新种子 → 二维码给手机扫
                                   ↓
新种子派生 KEK → 包裹同一个 DEK → 写新的 TOTP slot
```

最后一步是关键：把新种子**绑定**到这个 vault 必须持有 DEK，而纯动态模式下只有恢复密钥能取回 DEK。

**先分清"丢"的是哪种：**

| 情况 | 做法 | 需要恢复密钥吗 |
|---|---|---|
| 本机缓存丢了，手机种子还在 | 从手机导出 otpauth 粘一次 | 不需要 |
| **手机验证器里的种子也丢了** | 恢复密钥进去 → 生成新种子 → 扫码绑定 | 需要 |

**重要后果**：重绑后旧种子作废（打不开这个 vault 了，这是好事），但**笔记一个字节都不用重新加密**——DEK 没变，只是"装 DEK 的盒子"换了。

**术语纠正**：不存在"忘记动态密码"。6 位码每 30 秒由种子现算，不会忘；真正会丢失的是**种子**。

### Q4：多个用户装了同一个插件，种子会不会都一样？

**不会。** 这是把"代码"和"代码的运行结果"混为一谈了。

插件里装的是**生成算法**，不是种子本身：

```ts
export function generateTotpSecret(): string {
  return toBase32(randomBytes(20));  // 每次调用都现生成
}
```

所有用户下载到的 `main.js` 确实是同一个文件，但每个人在自己的设备上运行这个算法时，`randomBytes(20)` 产生的是不同的随机数。实测连续四次生成：

```
第1次: 2VVURZFCM5O3XMR3I7DS
第2次: DPYKG4DPUVW57L2V6ZIP
第3次: 3XPGDHWVZCGWCSBB7VWR
第4次: MW3AGJDSG2XYGG4JCAIP
```

四个完全不同。代码里 grep 不到任何写死的种子字符串（文档里出现的 `JBSWY3DPEHPK3PXP` 是 RFC 6238 的标准测试向量）。

推广一下，这个插件里所有随机值都是这样：

| 随机值 | 生成时机 | 作用 |
|---|---|---|
| DEK | 每个保管库初始化时 | 加密所有笔记 |
| 恢复密钥 | 每个保管库初始化时 | 重设密码 |
| TOTP 种子 | 每个保管库启用动态密码时 | 第二因素 |
| PBKDF2 盐 | 每个 slot、每篇笔记 | 防止彩虹表 |
| GCM IV | 每次加密 | 相同明文不同密文 |

**都是 `randomBytes()` 现场生成，没有一个写死在代码里。** 所以两个用户装同一个插件，就像两个不同的人用同一本菜谱做菜——成品各不相同。

**只有一种情况两个人的码会一样**：你把 otpauth 链接发给对方，他导入了**同一个种子**。那是你主动复制了一把钥匙给别人，等于把第二因素共享了——这不是 bug，是设计上就无法阻止（你拥有种子，就能复制它）。

反过来说，同一个人在同一台设备上，无论打开解锁框多少次，种子始终是同一个——因为种子只生成一次，固定存在手机验证器里。

### Q3c：拿到本机存储的数据，能自己算出动态密码吗？

**能，但要同时拿到两样东西。** 这是必须诚实写明的信任边界。

localStorage 里存的是**设备密钥**（32 字节随机），不是种子本身。笔记里的 `seedRef` 是被这把设备密钥加密的种子。攻击者若同时拿到：

1. 本机的设备密钥（本机管理员权限、恶意程序可读）
2. 笔记里的 `seedRef`（云端泄露即可拿到）

就能用 AES-GCM 解出明文种子，再用 `HMAC(种子, 时间)` 算出任意时刻的 6 位码——**不需要你的手机**。更进一步：有种子就能解 TOTP slot 拿到 DEK，进而解开所有笔记。

这个后果已经写脚本实测验证：给定设备密钥 + seedRef，确实能还原出原始种子。

**但攻击面被限制在这台机器上：**

| 攻击者拿到的 | 能否算码/解开笔记 |
|---|---|
| 只有云端同步的笔记（含 seedRef） | ❌ 没有设备密钥，解不开种子 |
| 只有本机存储，没有笔记 | ❌ 没有 seedRef，没有种子可解 |
| **两样都有**（本机被完全控制） | ✅ 能算码、能解 DEK |
| 换了台新设备 | ❌ 新设备密钥不同，旧 seedRef 解不开，需恢复密钥重绑 |

**这就是本地加密的固有边界**：TOTP 是应用层门禁，不是密码学强制。如果攻击者已经完全控制了你的机器（能读本机存储 + 能读 vault 文件），任何本地插件的"第二因素"都挡不住他——因为密钥和密文都在他手里。

**它仍然防的是**：云端同步泄露、别人拿到你的 vault 文件但没你电脑、换设备时旧密钥不可用。这些才是现实的威胁模型。

要防"本机被完全控制"，只能上硬件密钥（YubiKey / WebAuthn），那超出 Obsidian 插件的能力范围。

### 最容易搞错的一句话

有人把恢复流程理解成："恢复密钥派生新设备密钥 → 结合手机种子 → 把所有文档重加密一遍"。

**三处都错**，请记住这个最短版本：

> 恢复密钥只负责**让你进去**（解出 DEK）。设备密钥是插件**自己随机生成**的，跟恢复密钥无关。文档用 DEK 加密，**DEK 没变所以文档一个字节都不动**。从手机导入同一个种子，只是让新设备密钥重新封存它。

三个角色各管各的：

| 层 | 用什么 | 设备密钥丢了会怎样 |
|---|---|---|
| 文档内容 | `AES-GCM(HKDF(DEK), 内容)` | **不变**，DEK 没动 |
| 解锁盒子 | 密码/恢复密钥/种子各自包 DEK | 不变，只是用恢复密钥解开一次 |
| 本机种子缓存 | `AES-GCM(设备密钥, 种子)` | **只有这层变**：新密钥重新封存同一个种子 |

### 设备密钥丢了，能用手机种子"算回来"吗？

**不能。** 这是两个完全独立的随机数：

- 设备密钥 = `randomBytes(32)`，本机生成
- 种子 = `randomBytes(20)`，设置时生成，存你手机

它们的关系只有一个方向：

```
设备密钥 --AES-GCM 加密--> 种子密文(seedRef)      ✅ 正向成立
种子密文 --???--> 设备密钥                         ❌ AES-GCM 单向，推不出
手机种子 --???--> 设备密钥                         ❌ 两者毫无推导关系
```

设备密钥从没上过手机、从没同步，手机种子里不包含任何关于它的信息。所以"用 Authy 的种子找回 localStorage 密钥"这条路在密码学上不存在。

### 那设备密钥丢了要不要"重置动态密码"？

**不要。** 这是两种操作的本质区别：

| | 设备密钥丢了 | 手机种子也丢了 |
|---|---|---|
| 恢复密钥的作用 | 只是让你**进去**（解 DEK） | 进去 + 重设动态密码 |
| 种子 | **不变**，从手机重新导入 | **换新的**，要重新扫码 |
| 新设备密钥 | 自动生成，重新封存种子 | 自动生成，封存新种子 |
| 手机要扫码吗 | **不用** | 要 |

正确流程（设备密钥丢、手机种子还在）：

```
① 旧 seedRef 解不开 → 6 位码进不去
② 用恢复密钥解锁（它不依赖种子）→ 拿到 DEK
③ 设置 → 恢复本机种子缓存 → 粘贴手机导出的 otpauth 链接
④ 插件自动生成新设备密钥，用它重新封存【同一个种子】
⑤ 恢复日常：只输 6 位码
```

**全程种子不变，手机不用重新扫码，6 位码照常。** 恢复密钥在这里只是"让你进门"，不是"重置动态密码"。

只有**手机上的种子也没了**（换手机、Authy 数据找不回），才需要走"重置"：恢复密钥进去 → 生成全新种子 → 新手机扫码 → 旧种子作废。

### localStorage 被清掉会怎样？

（`Q2` 已详述，这里补一句术语）清掉后**不能自动恢复**：重新生成的是新设备密钥，不是种子；新密钥解不开旧 `seedRef`。需要从手机验证器导出 otpauth 链接粘贴一次，之后恢复"重启只输码"。

### 三种解锁模式的凭据流图

```
模式 A：纯主密码
  输入 主密码
    → credentialFor = "sn-pwd|<密码>"
    → PBKDF2(600k) → KEK
    → AES-GCM 解开 slot.password → DEK
    → 解密笔记

模式 B：纯动态密码
  输入 6 位码  ＋  本机种子(seedRef 解出)
    │                │
    │                └─ verifyTotp(种子, 码) → ✓ 验证门禁（码不参与加密）
    │
    └─ credentialFor = "sn-totp|<种子>"
    → PBKDF2(600k) → KEK
    → AES-GCM 解开 slot.totp → DEK
    → 解密笔记

模式 C：密码 + 动态密码（一个盒子，不是两个）
  输入 主密码 + 6 位码  ＋  本机种子
    │           │              │
    │           │              └─ verifyTotp(种子, 码) → ✓ 只验证
    │           │
    └─ credentialFor = "sn-pwd-totp|<密码>|<种子>"
    → PBKDF2(600k) → KEK
    → AES-GCM 解开 slot.password-totp → DEK
    → 解密笔记

恢复密钥（任何时候都能进）
  输入 52 字符
    → "sn-rec|<规范化>" → PBKDF2 → KEK
    → 解开 slot.recovery → DEK
    → 重包任意 slot / 读笔记
```

**三条共性**：

1. 6 位码**只出现在验证环节**，从不进 PBKDF2、从不参与加密
2. 真正进 PBKDF2 的是种子（模式 B/C）或密码（模式 A/C）
3. 四条路最后都解得**同一把 DEK**，所以模式随便切、笔记不用重加密

### 三个概念的最终对照

| 概念 | 是否固定 | 是否参与加密 | 存在哪 |
|---|---|---|---|
| **种子 secret** | 固定不变 | ✅ 是（派生 KEK） | 手机验证器 + 解锁时的插件内存 |
| **6 位验证码** | 每 30 秒变 | ❌ 否（只做验证门禁） | 屏幕/你的输入，用完即弃 |
| **加密后的 DEK** | 换凭据才变 | ✅ 是（真正加密内容） | 笔记的 `keys` 字段（随同步走） |

## 12. 插件怎么判断验证码对不对？

一个常见疑问："Authy 随机出来的码，插件怎么知道对不对？要不要问 Authy？"

### 不问 Authy，插件自己算

Authy 和插件用**同一个种子 + 同一个时间**，各自独立算出 6 位码。两边一样就通过。

```
手机 Authy:  HMAC(种子, T) → 6 位码  → 显示给你
插件自己:    HMAC(种子, T) → 6 位码
                     ↓
                逐字符比对 → 相同则通过
```

插件从不联系 Authy，也不读取手机时间。它只比对"你输进来的数字"和"它自己算出来的数字"。

### 三个判定细节

**1. ±1 步容错**

插件实际算三次：当前 30 秒窗口、前一个、后一个（覆盖总共 90 秒）。任何一次匹配就通过。这样即使你看到码的同时刚好跨过 30 秒边界，或者手机和电脑差几秒，都能通过。

实现见 `src/core/totp.ts`：

```ts
for (let drift = -TOTP_WINDOW; drift <= TOTP_WINDOW; drift++) {
  const expected = await totpCode(secret, { now: now + drift * step * 1000 });
  if (timingSafe(expected, cleaned)) return true;
}
return false;
```

**2. 格式清洗**

输入里的非数字会被剥掉（空格、连字符都可以），剩下必须是 6 位。长度不对直接失败。

**3. 恒定时间比较**

不用普通的 `===`，而是逐字符异或累加：

```ts
let diff = 0;
for (let i = 0; i < a.length; i++) diff |= a.charCodeAt(i) ^ b.charCodeAt(i);
return diff === 0;
```

这样"匹配"和"不匹配"耗费的时间几乎一样，避免通过响应时间推断你猜对了几位。这是密码学工程的标准做法。

### 失败的处理

验证失败 → 抛 `UnlockError`（标记 wrongSecret）→ 解锁服务计入 failCount → 连续失败触发指数退避等待。弹窗重新打开让你重试。

### 最关键的一点：验证通过 ≠ 用这个码解密

验证只是门禁。通过后插件用的是**种子**：

```
verifyTotp(种子, 6 位码)        → 通过，证明你手机里有种子
credentialFor("sn-totp|种子")   → PBKDF2 → KEK
KEK                            → 解开 DEK
DEK                            → 解开笔记
```

6 位码从不参与加密，用完即弃。因为它是 20 位熵且每 30 秒变——拿它当密钥，攻击者枚举 100 万次就能破，而且 30 秒后自己都解不开自己的笔记。

## 13. 常见问题

### Q：二维码会被别人扫到吗？

只在设置时显示一次，关掉弹窗就没了。截图等于交出种子，别截图。

### Q：otpauth 链接要备份吗？

**要。** 换手机时用它迁移。存密码管理器，别存云笔记明文。

### Q：手机没网能看验证码吗？

能。TOTP 只需要种子和本机时钟，不需要网络。

### Q：手机和电脑时间差多少会失败？

超过 30 秒（1 步）可能失败，超过 90 秒（±1 步窗口）必定失败。开自动时间同步。

### Q：验证码被偷看了怎么办？

30 秒后失效。但攻击者如果同时拿到了笔记 + 你的主密码（双因子模式），还能试——不过没有种子就过不了验证。这就是第二因素的价值。

### Q：为什么叫 TOTP？

**T**ime-based **O**ne-**T**ime **P**assword，基于时间的一次性密码。RFC 6238。

### Q：和 HOTP 有什么区别？

HOTP（RFC 4226）用计数器，每用一次 +1；TOTP 用时间当计数器。TOTP 更适合"不用记录用了几次"的场景，所以 App 都用 TOTP。

### Q：种子 160 位，为什么二维码才 32 个字符？

Base32 用 5 位表示一个字符，`160 / 5 = 32`。不是压缩，是换了一种表示法。

### Q：插件把种子存在哪？

**明文种子不落盘、不进笔记、不同步。** 解锁时从本机 `seedRef`（设备密钥加密的种子副本）解出，放在内存 `sessionTotpSeed` 里供本次会话使用；重启后从 `seedRef` 自动恢复，日常只需输 6 位码。只有换新设备时才需要粘贴一次 otpauth 链接。写进笔记的只有"用种子派生 KEK 包裹后的 DEK"和设备加密后的 `seedRef`，都不是明文种子。详见[第 11 节](#11-种子在插件的哪里多设备一致吗)。
